Internals of HDFS
=================


Let us consider we have 4 node cluster and have huge file with 500 Mb

Now instead of storing that file in a single machine we will split across all the machines.

to split the file there is a concept called block size - 128 mb (Hadoop 3)

After splitting file data into multiple block and storing it in different nodes when some one tries to read the file1. They donot know what is kept where so we require a master node (Name Node) and remaining 4 slave nodes (Data Node)

Name Node - Holds metadata of what is kept where in a tabular format (file1 | b1 | DN1)

Whenever customers wants to read file1 request will go to Name Node (Master) and it will checkout the metadata table and then it will reach out to the Data Nodes accordingly to fetch the data.


block size - 128 mb (Hadoop 3)

1 Name Node (Maste Node)

multiple data nodes 

data nodes hold actual Data

Name Node hold metadata table that contains what is kept where (ie which block of data is present on which Datanode)

Name Node is made of cheap or less cost Hardware


How to make sure that we dont loose data even when a data node goes down
------------------------------------------------------------------------

Replication factor comes into picture --> each block will have 3 copies by default (Example:- b1 stores in node1 and also gets stores in another 2 nodes). So once machine goes down then we can use the other two machines to access data. 

*********** Block Size and Replication factor can be changed by Admin *************


How does Name Node get to know that Data Node is down
-----------------------------------------------------

Heart Beat concept --> Every Data Node sends a heart beat to namenode for every 3 seconds indicating its alive.

If Name Node does not receive heart beat for 10 consecutive times then Name Node will assume Data Node is dead and it will remove that Data Node and replicate the block of data present in that Datanode to another Datanodes 

What if Namenode fails
----------------------

Datanode is cheap hardware but not Namenode, so chances of Namenode failing is very less. But if it fails there is a concept of Secondary Namenode. There is a process to copy the data from Namenode1 to seconday Namenode and it is Admins reponsibility.

***** Without Namenode we dont know which block of data is present on which Datanode *****

HDFS
====

Let us consider that we have 4 datanodes, 1 namenode Hadoop cluster and file1 with size 500mb. Max we can have 4000 datanodes.

Why block size is 128Mb? what happens if we reduce the block size to 64 mb
--------------------------------------------------------------------------

1 Gb file - default block size is 128 Mb - 8 machines max
1 Gb file - default block size is 64 Mb - 16 machines max
1 Gb file - default block size is 32 Mb - 32 machines max

If we reduce the block size, it leads to more number of blocks. Then there will be more parallelism.

If we choose a block size very low i.e 1Mb and you have a file of 10Gb, there will be 10240 blocks then you need 10240 machines at max. 
In this case, namenode has to keep the metadata of all these blocks in its table and it will get overburdened with these many entries.


What if we increase the block size
----------------------------------

1 Gb file - default block size is 128 Mb - 8 machines max
1 Gb file - default block size is 256 Mb - 4 machines max
1 Gb file - default block size is 512 Mb - 2 machines max

Then there will be less parallelism.

We basically need to ensure that we should not overburden the Namenode and it should give us appropriate parallelism. So we got 128mb block size.

If your data grows then we can add more number of Datanodes.

When your datanodes increases to a certain level then your metadata also would have grown up. In that case single Namenode will become a bottleneck. Because single Namenode will get overburdened with metadata.

In newer version of Hadoop, there is a concept that called "Namenode Federation".

Namenode Federation -> we can have more than 1 Namenode. Metadata is split across these namenodes.

For example, Sales department metadata is handled by Namenode1, Finance department metadata is handled by Namenode2. These kind of namespaces can be created and hanlded by particular namenodes.

********* Namenode Federation concept is to give Scalability to make sure Namenodes are not overburdened *********


Datanode Failure
----------------

Replication factor - by default 3 copies of each block of data is created.

Namenode Failure
----------------

Secondary Namenode will replace the failed namenode and admin will take care of copying the metadata of failed namenode to Secondary Namenode.

Secondary Namenode vs Namenode Federation
=========================================

Secondary Namenode --> Fault Tolerance (Its a backup plan when a namenode fails)
Namenode Fedaration --> Scalability (When metadata increases we can add more namenodes)

HDFS vs Cloud Datelake
======================

HDFS cloud alternatives are Amazon S3, ADLS Gen2 (Datalakes in cloud)

If I am running pyspark or spark code, then I would treat HDFS and Cloud Datalake storages in the same way and I can use both of them in same way. But there is 1 major difference.

HDFS + pyspark (Good combination)

ADLS Gen2 + Databricks (Good combination)

HDFS - distributed file system (data is stored in the form of blocks)

ADLS Gen2/ Amazon S3 - Object based storage (data is the stored in form of objects)

Object has id - Unique Identifier
		   value - the content which we are storing
		   metadata - who can access the file, what kind of data is stored and others
		   
Differences between Distributed File System vs Object Based Storage (HDFS vs Amazon S3/ADLS Gen2)
=================================================================================================

HDFS is not persistent where are Amazon S3 and ADLS Gen2 are persistent

what do you mean by persistent?
-------------------------------

Let us consider we have 4 node Hadoop Cluster i.e 4 datanodes.

what if we shutdown/terminate the cluster. We will loose the data. That is your storage is tightly coupled with compute. 

If you want just to store the data but not compute i.e you just want to store the data in HDFS but you dont want to do any processing. Even then we need to pay for the compute cost also because the 4 datanodes are that are running is having both compute and storage. So we cannot only pay for storage.

When you want to increase the storage in your Hadoop cluster we cannot just add the storage when we add a datanode it will have both storage and compute which will endup paying more cost.

In simple terms in case of cloud, storage is not coupled with compute. So we just need to pay for compute only when we do some processing otherwise pay for storage alone. Here storage is cost effective and compute is comparitively costly.

One more disadvantage with HDFS is that,
if we have one Hadoop - 4 node cluster (HDFS Datalake)
another Hadoop - 8 node Cluster, if 8 node cluster tries to access the data from 4 node cluster HDFS it is not possible. 
That means if i am using 4 node cluster data is valid data is valid for that cluster only other clusters cannot access the data. It work in sylos.

But in case of cloud datalakes (Amazon S3/ADLS Gen2) any number of clusters can use this data for processing. That means compute and storage are not tightly coupled with eachother in any cluster.

code is going to the data and as it will be very small in size i.e few kilo bytes. so we send code to the data and data is processed on the machine where it is kept. This is what we call as "Data Locality".

Mapreduce is used to process huge amount of data. It doesnot make sense to use Mapreduce to process small amount of data. Because in terms of coordinating the work for Mappers and Reducers itself will take lot of time. So dont use Mapreduce programming paradigm for small data.

Changing the Number of Reducers
===============================

What is the need to change the Reducer from default - 1 to another number

When should we consider to increase the number of Reducers
----------------------------------------------------------

5 Mappers are able to complete the work in few mins (2 min) and 1 reducer is taking long time (10 min) to do the work. (12 mins)

Now we tried to shift some of the computation from Reducer end to Mapper end 

So 5 Mappers are able to complete the work in few mins (3 min) and 1 reducer is taking long time (5 min) to do the work. (8 mins)

*** Beyond this we are unable to optimise more by giving more computation to Mappers as we need to do aggregations which can by done Reducers only ***

In such case, if we have 5 Mappers (3 min) and 2 Reducers (2.5 min) we can finish works in 5.5 mins because of parallelism in Reducers also. Whenever we feel there is a bottleneck/overburdened bcz of 1 Reducer we can have more reducers. But more parallelism should be done at Mapper end but not at Reducers end.

When should we consider to reduce the number of Reducers to 0
-------------------------------------------------------------

There can be few jobs which do not require aggregation.

In case of Filtering scenario, only mappers can do the filtering. In such scenarios we dont require shuffle, sort and aggregate and Mapper output will be final outpu and we dont require Reducer.

Shuffle and sort only happens when we have 1/more Reducer.

So when there is no Reducer or Reducer Number is 0 then your mapper output will be the final output.

If File is 1Gb in size, then we are doing some filtering. We will have 8 output files as Mapper output will be the final output. As per block size of 128Mb we will have 8 blocks for 1Gb of file, so eventually we will have 8 Mappers and 8 output files will be there...


Scenarios
---------

Consider we have 3 Mappers and 1 Reducer, output of 3 Mappers will go to the same Reducer without any logic.

Concept of partitioning comes into picture when we have more than one reducer. This will tell which k,v pair goes to which reducer
----------------------------------------------------------------------------------------------------------------------------------

Logic involved in this is, by defualt there is "System Defined Hash Function" which tells you that which k,v pair goes to which partition and eventually to which Reducer

Consider we have 3 Mappers and 2 Reducers, 
Mapper 1 has 10 (k,v) pairs --> k,v pairs are given equally to both Reducers to maintain equal work distribution. Now Key concept of partitions will come into play i.e output of Mapper 1 will be divided into two partitions. 

***** Partitioning of Mappers output is based on the no.of Reducers we have (no.of partitions = no.of reducers) *****

all partition 1's go to reducer 1 and all partition 2's go to reducer 2

Example:-

mod

3 Reducers - 0,1,2

keys (for numeric)
-----------------
1%3 = 1
2%3 = 2
3%3 = 0
4%3 = 1
5
6
7

Keys (for string) --> ASCII values are considered

Hash Function is consistent...

explanation for consistent
--------------------------

if we have, same key should always go to same reducer (i.e consistent) bcz if hello goes to different reducer we cant get the total count of hello
(Hello,1) --> Assigned to Reducer1
(hi,1) --> Assigned to Reducer2
(hello,1) --> Assigned to Reducer1

*** By default Hadoop uses, system defined Hash Function to divide the k,v pairs. This Hash Function is consistent so that if a key repeats any number of times it is assigned to the same reducer ***


scenario (Not to use system defined Hash Function)
--------------------------------------------------

All the words whose length is less than 4 chars should go to Reducer1 and all other words whose length >= 4 chars should go to Reducer2. 

If you dont want to use the system defined hash function then in such cases we need to write our own custom partitioning logic to divide the k,v pairs that goes to the Reducers for aggregation. 

But in this scenario also if you have same words with length < 4 chars (hi), then we have to follow system defined Hash Function i.e as "hi" word should go to only 1 Reducer either Reducer1/Reducer2

Examples for inconsistent function:- 
1) conversion of Dollars to Rupees 
2) finding out only the unique words in the paragraph (We dont follow system defined Hash Function)

But we need to make sure our Hash function should be consistent always!!!


Flow of Mapreduce
-----------------

Record Reader --> Map --> Partition, Shuffle, Sort --> reducer

Record Reader --> To internally convert the lines to k,v pair

Map -->  this gives us parallelism bcz Mappers will be running on different Machines

Partition --> when we are having more than 1 reducer to determine which k,v pairs will go to which reducer (Happens on Mapper Machine)

Shuffle --> Mappers output is send to the Reducer

Sort --> k,v pairs get sorted on the Reducer (Happens on Reducer Machine)

Reducer --> this is for aggregation of Mapper results 

What is shuffle?
---------------

Sending the data from Mapper Machine to Reducer Machine, so that Reducer machine gets the data to work on.

What is sort?
-------------

Operation done on Reducer Machine to get the same keys together in a group. (hello,{1,1,1})

Values with same keys appear as a collection/list to the reducer and reducer will perform the aggregation or sum it up.

Hadoop - HDFS / Mapreduce / YARN

Challenges with Mapreduce
-------------------------

1. Performance - Lot of DISK IO's required

2. Its really hard to write the hundreds of lines of code in Java.

3. Mapreduce supports only Batch Processing
	- Batch processing - loading data at regular interval of time
	- Realtime processing/streaming - deals with current flowing data/streaming Data
	
4. Hive (Querying), Pig (Scripting Language for programming), Sqoop (Data Ingestion), HBase (Nosql), Oozie (workflow scheduler) we need to learn a lot of tools or technologies.

5. Map Reduce - We talk only about Map and Reduce, though our problem might not be bcz of Map and Reduce but we try to adjust and try to resolve those issues only using Map and Reduce. Example: Filter, map will work but reduce won't...

6. Intreactive mode - There is no intreactive mode like linux commands. Instead we bundle the jar/code and run it on the cluster and we wont get the response for each command that we execute from the cluster.

Apache Spark
============

It is meant for Distributed Processing to overcome the Challenges with Mapreduce. It is just a Compute Engine.

Spark does not come with storage and resource manager. It is a plain compute engine that supports only Distributed Processing. When we have some huge number of machines holding the data then spark can help us how to process the data across the cluster of those machines as traditional programing methods wont work.

Spark requires we need 2 things to work. 

1. Datalake
2. Resource Manager

It is just a plug and play compute engine it can work with any Datalake (storage) [HDFS / S3 / ADLS Gen2 / GCS / local] 
and Resource Manager [YARN / Mesos / Kubernetes] of our choice.

Apache Spark is a multi language engine for executing Data Engineering, Data Science, Machine Learning on single node or cluster.

Mapreduce we write code in Jave. But Apache Spark is a multi language engine we can write in scala, python, java & R.

Python + Spark = PySpark 

Apache Spark is a general purpose, in-memory & compute engine.

General Purpose -> In Hadoop we need to know different components to work with different requirements i.e Hive for querying, Sqoop for Ingestion, pig for scripting but here Apache Spark is enough to work with different requirements. 
					
In-Memory -> Process the data/keeps the date in memory, bcz of this it is 10x-100x faster than Mapreduce.

Compute Engine -> requires any storage and resource manager to work with.

Scenario:-
--------

Let us consider we have Mapreduce jobs MR-Job-1, MR-Job-2, MR-Job-3, MR-Job-4, MR-Job-5. In this case 10 DISK IO's are required bcz each MR job has to take the input data from HDFS Disk, do the processing and output will be written on the DISK HDFS. When we have a series of MR jobs it happens through DISK HDFS only. This read and write of Data from/to HDFS DISK take time Which will create delay in the performance.

*** Best Scenario ****
In Spark, Job1 output is not written back to HDFS DISK instead, Job1 output will be passed over to Job2 and this will happen in-memory and the last job output will be written back to HDFS DISK which will reduce the DISK IO's to 2. We will do all the calculations in-memory. 

For a chain of 5 Mapreduce jobs - 10 disk IO's 
but in spark it could be as min as 2 disk IO's

Spark lets you focus on WHAT computation you want, while Spark handles HOW that computation is distributed across the cluster

How things work in Apache Spark?
===============================

Let us consider we have a file named file1 in HDFS of size (512Mb).

--> I will write a code to bring it to Memory from HDFS as below, and whenever I load the file1 from HDFS, it will come to in-memory and we give it a name as rdd1.

1. rdd1 = Load file1 from Datalake (HDFS / Cloud Datalake) 

--> we are storing the results of rdd1.map transformation into "rdd2"

2. rdd2 = rdd1.map

--> we are performing filter transformation on rdd2 and stored the results into "rdd3"

3. rdd3 = rdd2.filter

--> to get the results on the screen

4. rdd3.collect()

when we run 1,2,3 nothing will happen, but when we run 4 everything will happen. Basically after running 1,2,3 internally these lines were added to a plan and when we run 4 it execute.

There are 2 kind of operations in Apache Spark
----------------------------------------------

1. Transformation (Step 1,2,3) 
2. Action (step 4)

Transformations are lazy but actions are not i.e whenever transformations are applied they are added to execution plan and Whenever action is called/run the whole execution plan gets executed.

Execution plan flow will look like 
----------------------------------

This diagram we call as "DAG - Directed Acyclic Graph"
 
file1
  |
  |  (load) 
  |
RDD1
  |
  |  (map) 
  |
RDD2
  |
  |  (filter) 
  |
RDD3
  |
  |  (collect) 
  |
execution plan will get executed 


In spark, we have driver and multiple worker nodes

RDD is Resilient to failures, it means if something goes wrong we will not loose RDD/ it wont impact us.

How to make sure RDD is Resilient to failures
---------------------------------------------

If I loose RDD3, we can take the parent of "failed RDD" and apply the same transformation on it and we can regenerate it. (System automatically will do this).
So whenever we create new RDD it acts like a savepoint/lineage and supports fault tolerance. Because if we make all the transformations on a single RDD1 if we loose it, we dont have the parent RDD so we cannot regenerate it.

RDD's are immutable.
That means you cannot make changes to the existing RDD.
You end up creating a new RDD always for every transformation.

/* HDFS is Resilient with the help of Replication Factor
RDD is Resileint with help of Immutabiliy and Lineage */

Why transformations are lazy?
----------------------------

Materializing the RDD, i.e whenever we load the file1 from Datalake we will get some data into RDD1. As per concept RDD's are immutable.

rdd1 = Load file1 from Datalake (HDFS / Cloud Datalake) --> if we do this load, we will have content in RDD1 -> this we call as Materializing the RDD.

Benifits of Laziness

rdd1 = Load file1 from Datalake (HDFS / Cloud Datalake)
rdd2 = rdd1.map
rdd3 = rdd2.filter
rdd3.collect()

Let us cosider that we have a file in HDFS with 1 Billion records.

We are writing step 1, to load the file from HDFS as rdd1. 

#print the first line from rdd1... (pseudo code)

If spark is not lazy, we would have loaded 1 billion records in-memory just to print the first line from rdd1.... 

Spark being lazy, instead of loading 1 billion records in-memory, it gets only the required information/data/result which I have to display in-memory and only 1 line get into the memory and it will be printed.

Laziness helps to optimise the amount of data loaded into memory.


Spark is not lazy
-----------------

Let us consider we are having a file "file1" with 1 billion records and in this case whenever we load the file from HDFS, it will load 1 billion records to memory and then it will process 1 billion records row by row i.e it will take 1 billion records as input and generate 1 billion records as output by adding a new field to all 1 billions by using map transformation. And by using filter transformation we would like to filter for an employee based on employee id and want to get 5 records and return on the screen. 

The above procedure is a delayed bcz it needs to work with 1 billion records.


rdd1 = Load file1 from Datalake (1 billion records)
rdd2 = rdd1.map (1 billion records)
rdd3 = rdd2.filter (5 records)
rdd3.collect()

Now Spark being lazy
--------------------

Every step will be added as a part of "Execution plan DAD". Only when we run collect then it will load the file from HDFS.

Instead of map, it will filter first. It will save a lot of time bcz we need to add fields using map transformation only for 5 records.

Basically system will shuffle the transformations inorder to get the required results by optimising the performance.

All of our transformations falls under 2 categories

What is stage and why 2 stages in DAG?
======================================

Series of transformations that we want to execute is DAG.

We can have 1/2 stages but it depends on no.of wide transformations we have.

***** No.of stages = No.of wide transformations + 1 *****

What happens actually is, whenever we execute wide transformations then result of "Stage 0" is going to the disk and then "Stage 1" is taken from disk.

If we have 2 wide transformations, then it will be 3 stages. After every wide transformation the result will go back to the disk and write the output and next stage will take the result from the disk because shuffling will happen.

=====================================

Repartition vs Coalesce
=======================

Repartition
-----------

For example we have 1 Gb file and we created rdd and it will have 9 partitions which is equal to 9 blocks in HDFS.
we can increase or decrease the number of partitions.

When do we Increase the partitions? (To get more parallelism)
----------------------------------

Let us consider, we have 100 node cluster and we have 5 Gb file --> 40 blocks --> 40 partitions.

So at max less than equal to 40 machines are going to be handle the 40 partitions in parallel, remaining 60 machines will be idle. In this case we can increase the number of partitions inorder to get more parallelism. 

How do we increase?
------------------

From above scenario, 

Run --> rdd.getNumPartitions() --> output:- 40 (for rdd no.of partitions will be same)

Now to increase the partitions,

--> repartitioned_rdd = rdd.repartition(80) (here for rdd we applied repartition and saved in another rdd "repartitioned_rdd")

Run --> rdd.getNumPartitions() --> output:- 80

****** Repartition can increase or decrease the number of partitions in a RDD ******

When do we Decrease the partitions?
-----------------------------------

Let us consider that we have 100 node clusted and a 1Tb file | 8000 blocks in HDFS | 8000 partitions in RDD.

Each node is handling around 80 partitions. 

Each partition would be handling 128 Mb of data.

After applying filter transformation, we are getting 1 mb of data.

8000 partitions each holding around 1 mb of data.

In this case, maintaining 8000 partitions is not ideal because the time to manage the tasks would become difficult.

So we want to reduce the partitions, bcz instead of having multiple partitions with sparse data. But better to have lesser partitions with filled data.

Example:- 80 partitions holding 100 Mb.

***** Overall meaning is that partitions should have some data, instead of sparse data *****

Increase --> when we want to get more parallelism

Decrease --> After tranformation when the data becomes very less in each partition, then we will merge some partitions


Coalesce
--------
It will just decrease the number of partitions in RDD but it cannot increase the partitions.

Repartition Decrease vs Coalesce
--------------------------------
Repartition
-----------
It will do complete reshuffling of data

Let us consider we have 4 partitions, to make it 8 partitions we need to shuffle the data.

Let us consider we have 40 partitions, you want to make it 10 partitions. It will do complete reshuffling of data, bcz it want to male sure that 10 partitions holding same amount of data.

Coalesce
--------
Let us consider we have 4 node cluster and have 8 partitions. If we want to make it to 4 partitions. 

Coalesce will try to merge the partitions on same machine and give us new partition (np). So that it can try avoid shuffling Whenever possible. 
But this new partitions can be of un-equal of size of data.

node1 - p1,p2 --> merge -->np1 
node2 - p3,p4 --> merge -->np2
node3 - p5,p6 --> merge -->np3
node4 - p7,p8 --> merge -->np4

When we want to decrease the number of partitions Coalesce will perform in a more effecient way compared to repartition decrease.

when we want to increase the number of partitions repartition is the only way as it gives more parallelism.

When we try to increase the number of partitions using Coalesce. It will not throw any error but the no.of partitions will remain same.


Cache
=====
we can cache our RDD.

Why we need to cache RDD and How to do?
--------------------------------------

Step 1. Execute the boiler plate code to create a sparkSession.
step 2. orders_base = spark.sparkContext.textFile("/user/itv028185/public/trendytech/orders/orders_1gb.csv")
step 3. orders_filtered = orders_base.filter(lambda x: x.split(",")[3]!= 'PENDING_PAYMENT')
step 4. orders_mapped = orders_filtered.map(lambda x: (x.split(",")[2],1))
step 5. orders_reduced = orders_mapped.reduceByKey(lambda x,y: x+y)
step 6. results = orders_reduced.filter(lambda x: int(x[0])<501)
step 6.1 sorted_results = results.sortBy(lambda x: x[0])
step 7. results.collect()
step 7.1 sorted_results.collect()
step 8. spark.stop()

Basically if we apply a list of transformations and at last we execute an action...
What will happen if we execute the action again? --> I think it wont execute from the scratch instead it will take the data from "cache"

I have executed all the steps from step 1 

If I run collet again, basically all the transformations will be executed from start.

Let us consider that below is our situation,

Stage1			Stage2			Stage3
------			------			------
t1				  t4			  t7
	
t2				  t5			  t8

t3				  t6			  t9

collect - Stage1 --> Stage2 --> Stage3
collect - Stage3

When we run "collect" command first time it will start executing the "execution plan" from Stage1 t1 - Stage3 t9 and it will return the output on the screen.
If we run the "collect" command again, it will start execution from Stage3 by skipping the Stage1 and Stage2 (we can see this in DAG Visualization).

Sometimes we might have done a lot of work and we want to keep that result instead of doing it again from scratch. i.e

Lets consider that we have applied 10 transformations which are very costly and we want to use the result RDD again and again. Then we will cache the RDD.

--> rdd.cache()

Cache is Lazy. It doesnot cache right now. It will be cached when we execute it (rdd.cache) one time using collect and from 2nd time execution becomes faster. 
But first time execution will take time as the execution starts from beginnig and the result will be cached.

Only when we do a lot of processing and when you dont want to redo all the transformations from the beginnig then go for "Cache". 
Basically it is not recommended or good caching the base_rdd as it consumes the memory.

Only cache the data when you feel that you have performed lot of processing/transformations i.e medium, small sized resultant data as it consumes memory.

When we run the "Cache" command you will a "Green" dot while loading the data from stage to Disk.

What if enough memory is not available for caching?
--------------------------------------------------

Caching will be skipped if there is no enough memory for storing the resultant data. It is always done in memory.

Persist vs Cache
----------------

Caching is always in-memory

Persist will give you more options like persist on disk, persist on memory, persist on memory and disk.

-----------------------------------------------------------

Till now we have gone through RDD's.

RDD's do not consist of any schema (metadata). Column Name, Data type. Its just a raw data which is distributed across the cluster in the form of partitions.

In RDD's there is no structure / schema / metadata associated with it.

Spark creators itself recommend not to use RDD/ avoid using code in RDD Whenever possible. Bcz it does not give you optimisation and easy to write the code, which we will get using Higher Level API's.

Lets consider that we have a table in a Database (orders). It contains 2 things.

1. Data (1,21-10-1997,101,CLOSED) --> Data will be present in the form of Datafiles in a physical storage (DISK) 

2. Metadata/Schema (columns names like order_id - INT, order_date - DATETIME, customer_id - INT, order_status - VARCHAR) --> Will be kept in Metastore, it is the place that contains metadata or holds the schema of it.


When we run,
	select * from orders 
metadata + data will get combine together and gives you output in the form of tabular view 

For example,
when we run	select order_id, order_date from orders,
then it will check the metastore, that whether the mentioned columns are exists in the table or not. If exists then it will go for the Datafile.
If not available it will give "analysis exception".

Same concept is applicable for Apache Spark.


Spark SQL contains 2 things.

1. Datafiles --> stores on the DISK - on your Datalake (HDFS, Amazon s3, ADLS Gen2, GCS)
2. Metadata --> stores in the Metastore - it can be some database where it is getting stored. Admin can configure where to store the schema/metadata.


Dataframe
---------
It is just like a RDD with some structure (Metadata/Schema)

Data is stored in memory
Metadata is also stored in memory

There is no metastore to hold the metadata. And your metadata is kept temporarily in metadata catalog. It will be gone once application is closed.

Spark Dataframs vs Spark Table
==============================
Spark Dataframe is not persistent. Only during the session we can see data and metadata, once we close the spark session we wont find data and metadata.

Spark Dataframes is available only for your session.

Spark Table is persistent. We use spark sql to write Spark Table. Data and Metadata will be available even after closing the spark session. We can see the data in the tables until we drop the table.

Spark Table is accessible acorss other sessions.


RDD's are not recommended... But we need to know how Spark Sql, Dataframes internally works as it works at higher level to RDD.

Dataframes and Spark SQL (Higher Level API's) are recommended...

Both Dataframes and Spark SQL gives us same level of performance. 

We can convert Dataframe to Spark Table and Spark Table to Dataframe.


Why Higher Level API's performance is better?
--------------------------------------------

Becuase whenever we create Dataframe OR Spark Table it is just like RDD + Schema (some extra information).

Spark engine would have better idea how to optimise things bcz we are provinding extra information i.e metadata (How many columns and their datatypes and total columns) and data.
